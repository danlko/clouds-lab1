# Навантажувальне тестування (завдання 2)

Інструмент — **k6**. Сценарій: [`loadtest/script.js`](../loadtest/script.js), запуск: [`loadtest/run.sh`](../loadtest/run.sh).
Якщо k6 не встановлено, скрипт запускає його в Docker (`grafana/k6:1.0.0`).

## Запуск однією командою

```bash
DEMO_EMAIL=you@example.com DEMO_PASSWORD='...' ./loadtest/run.sh
```

Скрипт сам бере адресу з `terraform output app_url` і отримує JWT Cognito (для POST; токен живе 60 хв, прогін — 9.5 хв).
Результати: консоль + `loadtest/results/<LABEL>-<час>.md` (таблиця для звіту) і `.json` (повні дані k6).

Локально (compose, без автентифікації): `BASE_URL=http://localhost:8000 ./loadtest/run.sh`.

## Сценарій

Один віртуальний користувач (VU) у циклі виконує **1 запис і 9 читань** (співвідношення 1:9):

| # | Запит | Тег `op` |
|---|---|---|
| 1 | `POST /books` — нова книга одного з 10 авторів | create |
| 2 | `GET /books?limit=50` — список найновіших | list |
| 3 | `GET /books/{id}` — щойно створена | get |
| 4 | `GET /authors/{author}` — дані автора щойно створеної книги | author |
| 5 | `GET /books?limit=50` | list |
| 6 | `GET /books/{id}` — випадкова книга зі списку | get |
| 7 | `GET /authors/{author}` — автор випадкової книги зі списку | author |
| 8 | `GET /books?limit=50` | list |
| 9 | `GET /books/{id}` — щойно створена (повторно) | get |
| 10 | `GET /books/{id}` — випадкова книга зі списку | get |

Між запитами — пауза `THINK` (0.3 с): імітує «час на прочитання» і робить навантаження керованим.

Фази (`ramping-vus`):

| Фаза | Тривалість | VU |
|---|---|---|
| Наростання | 2 хв 30 с | 0 → N |
| Стале навантаження | 5 хв | N |
| Спад | 2 хв | N → 0 |

Разом 9.5 хв (+30 с `gracefulRampDown`).

## Параметри

| Змінна | За замовчуванням | Значення |
|---|---|---|
| `VUS` (N) | 60 | кількість користувачів на сталому навантаженні |
| `THINK` | 0.3 | пауза між запитами, с |
| `RAMP_UP` / `STEADY` / `RAMP_DOWN` | 2m30s / 5m / 2m | тривалості фаз |
| `LABEL` | run | префікс файлів результатів |
| `BASE_URL`, `TOKEN` | з Terraform / Cognito | ціль і JWT |

Пороги (thresholds): частка помилок < 1 %, p95 для `GET /books` < 1 с — прогін позначається як невдалий, якщо їх порушено.

### Як підібрано N

Одна задача — 0.25 vCPU. Локальне калібрування (compose, `docker update --cpus 0.25`, 60 VU, кеш вимкнено):
~66 запитів/с, CPU контейнера впирається в ліміт (100 % виділеного), p95 ≈ 0.9 с.
Один VU генерує ≈ `1 / (THINK + латентність)` ≈ 3 запити/с, тобто 60 VU ≈ 150–190 запитів/с —
у 2–3 рази більше, ніж витримує одна задача при 60 % CPU. Отже на сталому навантаженні середній CPU
гарантовано перевищує ціль 60 % і сервіс масштабується до 3–4 задач. Якщо у хмарі масштабування не досягає 2+ задач —
збільшити `VUS` (80–100) або зменшити `THINK`.
