# Ідемпотентність операцій запису (бонус 7)

Код: [`app/idempotency.py`](../app/idempotency.py), підключення — `create_book` у [`app/main.py`](../app/main.py).
Сховище — той самий Redis, що й для кешу (завдання 5).

## Як працює

```
POST /books   Idempotency-Key: 5f0c…   (+ JWT)
  ключ у Redis: idem:<sub користувача>:<Idempotency-Key>
  1. SET key {"state":"processing","fp":sha256(тіла)} NX EX 60
     ├─ вдалося (перший запит) → INSERT у БД → SET key {"state":"done", status:201, body} EX 86400 → 201
     └─ ключ уже є:
          fp інший                → 422 (ключ повторно використано з іншим тілом)
          state = processing      → 409 (оригінальний запит ще виконується — повторіть пізніше)
          state = done            → збережені статус і тіло + заголовок Idempotent-Replayed: true
  Якщо INSERT упав — ключ видаляється, клієнт може повторити з тим самим ключем.
```

* `SET NX` атомарний — два паралельні дублікати не виконаються обидва.
* Ключ прив'язаний до користувача (`sub` з JWT) — чужий ключ не дасть прочитати чужу відповідь.
* Результат зберігається 24 год (`idempotency_ttl_seconds`); без заголовка поведінка як раніше.

## Яку проблему це розв'язує

POST не ідемпотентний: кожен виклик створює новий запис. Клієнт не може відрізнити «запит не дійшов» від
«запит виконано, але відповідь загубилась» (тайм-аут, обрив мобільного зв'язку, перезапуск задачі ECS під час
scale-in, 502 від ALB). Безпечно повторити можна лише якщо сервер розпізнає повтор. Клієнт генерує UUID на
*логічну операцію* і надсилає його при кожній спробі — сервер виконує операцію рівно один раз, а повторам віддає
той самий результат. Так поводяться платіжні API (Stripe), і так стає безпечним автоматичний retry у клієнтах і проксі.

## Як поєднується з чергою (завдання 6)

`POST /books/async` теж приймає `Idempotency-Key` (той самий `run_once`): повторний запит клієнта повертає збережену
відповідь 202 з **тим самим** `operation_id` і **не кладе друге повідомлення** в чергу.

Черга SQS доставляє «щонайменше один раз», тому дублікати можуть з'явитися й усередині системи. Захист на двох рівнях:

| Звідки повтор | Захист |
|---|---|
| Клієнт повторив POST (тайм-аут, обрив зв'язку) | `Idempotency-Key` у Redis → та сама відповідь, без нового повідомлення |
| SQS доставив повідомлення повторно (обробник упав до `DeleteMessage`) | `operation_id` — первинний ключ `operations`, `INSERT … ON CONFLICT DO NOTHING` в одній транзакції з книгою |

Ключ на вході захищає від повторів клієнта, ідемпотентний обробник — від повторів черги. Разом вони дають ефект
«рівно один раз» для бізнес-операції поверх доставки «щонайменше один раз». Деталі — [QUEUE.md](QUEUE.md).

## Обмеження реалізації

* **Redis і PostgreSQL не в одній транзакції.** У `run_once` ключ спочатку захоплюється в Redis (`processing`, TTL 60 с),
  потім `create_book` робить `commit()` у БД, і лише після цього в Redis записується `done` з відповіддю. Якщо Redis
  стане недоступний саме між `commit()` і записом `done`, книга вже збережена, клієнт отримає помилку, ключ лишиться
  у стані `processing` і через 60 с зникне — повтор з тим самим ключем створить **дубль**. Вікно дуже коротке, але воно є.
  Повне рішення — зберігати ключ ідемпотентності в PostgreSQL у тій самій транзакції, що й книгу (унікальний індекс
  `(user_sub, key)`), так само як це вже зроблено з `operations.id` в обробнику черги.
* **Redis без персистентності** (`infra/cache.tf`: лише пам'ять, без AOF/RDB). Якщо задачу Redis буде перезапущено,
  зникнуть усі ключі ідемпотентності — повтор запиту, зроблений після цього, виконається вдруге. Для продакшену —
  ElastiCache з реплікою або ключі в БД (див. вище).
